# 正式版基础系统 V1.1 技术评估与分阶段推进建议

> 2026-10-15 评审决定：用户确认正式版保留2～4人开局，普通成员掉线继续/原成员CP重连等其余系统按V1.1逐步推进。下文评估中的人数待确认项已关闭，3人开局门槛统一改按2人；伸缩保持独立实验。进入S0专项实现，其他估算仍非交付承诺。


评估日期：2026-10-15。代码基线：4c1fc24，国际版 Unity 6000.6.5f1。状态：供程序与策划评审，尚未批准的新规则不在本轮实施。

结论：现有原型可以作为正式版基础，角色运动、抓握物理和 Steam 传输不必推倒重来；但大厅会话、断线重连、检查点裁决和长期存档需要结构性改造。优先完成“合法开局—搬运—检查点保存—断线归队—退出再继续”的闭环，再补完整结算、装扮内容和界面表现。

## 1 规则边界与必须先对齐的差异

核心玩法继续以 V12 的 03 规则确认清单优先，其次 02 补充规则、01 历史基线。V1.1 用于后续正式版系统，明确修订的四柱 CP/终点判定单独记录；不追溯宣布历史 M2/M3 已完成。

| 项目 | 当前实现或此前用户决定 | V1.1 正式版目标 | 评估处理 |
|---|---|---|---|
| 开局人数 | 用户明确要求最少两人能玩，现版 2～4 人 | 单人可建房，但必须 3～4 真人准备后开局 | 这是产品范围差异。建议先请用户与策划确认正式版是否取消双人开局；开发测试入口继续保留双人 |
| 掉线/后来加入 | 用户选择暂停，人员到齐后从 CP 继续 | 普通成员断线后其余人继续，原成员在 CP 重连，不重置鱼缸 | 正式模式改造前确认取代之前暂停方案；原型验证结果保持原口径 |
| CP 激活 | 四柱顶部接触、线/角速度不大于 0.1、持续 0.2 秒 | 四柱同一权威物理步真实接触，无额外速度/等待条件；同一步危险优先 | 新增正式判定实现，不仅删除等待数值 |
| 伸缩 | 独立实验 B，Q/E；B 禁用 Ctrl 蹲下 | V1.1 仍列 Ctrl 蹲下，未纳入伸缩正式规则 | 暂不把 B 当正式默认；输入动作表须在实验结论后统一 |
| 云存档 | 用户曾提出正式版云存档方向 | 文档标记为技术评估项 | 推荐采用 Steam Cloud，作为正式发布前验收项；不阻塞先完成本地可靠存档 |

3～4 人允许开局、房主+1 先加载进入、开始后剩 1 人继续是三个不同条件，并非文档自相矛盾。但“系统允许继续”不代表剩 1～2 人一定能通过搬运关卡。应保留等待重连/投票复位等选择，不能擅自加入 AI、自动减重或扶正保证通关。

## 3 推荐技术方案

### 3.1 房主权威与 Steam 房间

保留“Steam Lobby 组织队伍，Steam 传输传消息，房主机器计算人物与鱼缸物理，其他端提交输入并显示快照”。不为当前熟人合作需求自建专用服务器。把逻辑房主 SteamId、Lobby owner、实际权威连接明确记录，不能混用。

当前 SteamCarrySession 同时承担平台、连接、世界、存档和 IMGUI。逐步分出会话状态、成员席位、存档服务、世界事件和界面，旧入口暂作调试适配；不要一次重写整个控制器。

会话建议顺序：主菜单 → 大厅 → 名单锁定/加载 → 实际游玩 → 结算中 → 报告完成/大厅。每个玩家的页面状态独立，避免房主先回大厅时强制关闭其他人的结算。身份来自已建立连接可验证的 Steam 对端，不相信客户端自报 SteamId。身份资格在 NGO 接入审批及游戏消息层都校验。

当前房间号就是 Lobby ID。第一版可保留可复制的完整数字码或无损编码，满足分享需求；短码不是文档硬指标。非好友加入需改房间可访问策略、测试 Lobby 行为，并在游戏层校验当前会话和资格。无公开房间列表不等于 Steam Lobby 必须 FriendsOnly。若以后一定要很短且不可枚举的码，再单独评估映射服务；仅把 Lobby 元数据写上六位码不能自动保证全球唯一或权限安全。

开局后平台可入房通道必须兼顾原成员重连：不能简单关闭所有 Lobby 加入就认为完成名单锁定。新人与重连资格由权威准入检查决定；拒绝者不得生成角色或影响已占席位。

Steam 官方说明 Lobby 所有者离开会自动转移，但这不是游戏物理主机迁移。首版采用 V1.1 §10.6 已允许的降级：权威房主异常离线，其他端结束会话回主菜单，保留最后可靠落盘的进度与统计，不把客户端观察到但未保存的 CP 当作已保存。无需新增无缝迁移承诺。

### 3.2 普通成员掉线与重连

以 SteamId 保留稳定席位，connectionId 仅是本次连接。区分在线、连接可疑、确认断线可重连、主动离队无资格、已结束。短时抖动不立即删角色；超时数值通过网络测试确定。过期输入需有有效期并禁止重复触发跳跃/抓取，不再用全局暂停掩盖网络问题。

确认断线后取消该角色抓取、被动支撑和碰撞实体，不修改鱼缸位置、旋转、速度。重连清理旧连接后只在最新 CP 生成该玩家，发送权威世界快照；不重置他人或鱼缸，默认未抓取且必须新的按下沿。主动离队需有效命令被权威接受；直接强杀按异常断线处理。

现版 M0CarryLab 重建时按 SessionTeamSize 缩放鱼缸质量，并有双人辅助。正式版中人数变化不应偷偷重算质量或瞬间切换支撑力造成跳变。建议每轮固定已选玩法配置；是否保留双人辅助、何时生效需要与开局人数决策一起确认。

### 3.3 四柱检查点和终点

不能只把 stableTime 改成 0。当前顶部接触字典没有显式模拟步编号，危险接触在碰撞回调直接 Fail，CP 在 Update 判断；一个渲染帧有多个物理步时，不能据此保证“前一步 CP 成功，后一步碎缸”不被吞掉。

建议按权威物理步聚合接触事实，在该步碰撞回调完成后统一裁决。每根指定柱使用稳定 ID；维护真实有效接触及退出/禁用清理，涵盖刚体休眠与持续接触，不能简单要求每步收到四次 Enter。裁决先危险，再终点/CP；事件包含 RunId、worldEpoch、physicsTick、eventId，接收端幂等应用。

可选择明确的物理步后处理或受控 Simulation 调用做试验，不在未验证时改全局模拟方式。系统出生使用新的 worldEpoch 和恢复标记，已激活 CP、已完成 Run 去重；正常碰齐四柱不增加任何等待/速度门槛。安全接触区域须在关卡资源中明确，不能继续无说明地把旧 normal.y > 0.5 当新规格。

先在小场景验证 3 柱、四柱立即触发、依次触碰不触发、同一步危险优先、前一步 CP 后一步碎缸、一次渲染多物理步、复位不重触发，再接正式路线。模型柱高/间距和碰撞网格需要关卡配合，不能靠加大触发区冒充真实接触。

### 3.4 五存档与云存档

沿用 CoopCampaignSave 的安全写入思路，建立 SteamId → 最多五个 SaveId → 当前 Run + 历史报告。分离当前 CP、累计计时/统计、个人设置与装扮。CP 是恢复位置，统计可以独立保存；退出时不保存任意物理位置。

建议每个槽以单个完整快照原子提交，或采用版本快照加提交清单，保证 Run 切换与历史引用一致。报告未增长到需拆文件前不必引入数据库；现存 1 MiB 限制应随历史容量测试调整。旧原型档不静默覆盖，迁移先备份、校验身份和 CP 映射；不兼容时保留原件并提示。

计时以权威端单调时钟累计，只计算 Playing/失败重试有效世界时间，退出大厅及加载不计；终点冻结。保存使用 revision 与事件 ID 去重，不以系统日期大小判断哪个存档必然更新。统计定期落盘及正常退出强制提交，崩溃可能丢失最后未提交片段；提交间隔是待测试/确认的损失上限，不能承诺断电零丢失。

重新挑战先保留会话意向；房主+1 已加载并即将解除世界加载屏障时，原子提交新 Run，成功后开始计时/控制。提交失败保持旧已通关 Run，给重试/返回，不让新轮进入可操作却无法保存的状态。

推荐正式版使用 Steam Auto-Cloud 同步明确的存档目录，先完成本地安全写入。Steam 官方提供 Auto-Cloud 与 RemoteStorage API 两条路线；Auto-Cloud 通常在启动/退出同步，不是实时游戏数据库。只同步稳定存档及经选择的个人资料，不同步锁文件、临时文件、日志、分辨率和机器画质。需要游戏内云冲突选择/上传状态时再评估 API 集成，不能把 Auto-Cloud 当已具备这些界面。

拿到本游戏 Steamworks App ID 和配置权限后，以两台设备测试；480 不能作为本游戏云配置已验收证据。不同设备分叉不按“CP 更大/时间更新”自动合并；保留恢复副本，呈现可区分的轮次/进度，确认选择策略。建议删除以二次确认加可诊断删除记录处理，具体可恢复期限仍由策划确认。

保存失败：显示“未保存”，保留上一有效版和待补写数据；提供有限重试、诊断导出及明确告知风险后的退出，不用无限弹窗锁死程序。通关事实先持久化为待结算记录，再收票，最后写不可变报告；中途崩溃恢复时如何截止未投票需确认，不能再次累加一次通关。

### 3.5 输入、统计和界面

正式 Input Actions 区分玩法输入、系统投票、UI/文字和改键捕获。ESC/Overlay 只释放本人的主动抓取，合法被动支撑保留；P 在普通菜单有效，在文字/改键/失焦状态无效。现版直接读键盘与网络 GM 暂停需改造，不能靠 UI 挡住鼠标就算完成。

20 秒复位票冻结发起时名单，掉线不缩减门槛，实际复位用最新 CP；与危险碎缸/终点竞争由统一世界事件处理。统计先建权威事件接口，只先落实冻结的时间、碎缸和 CP；个人候选事件与 RELEASE_GRAB 细分待确认后接入。不要用主观物理责任推算“谁撞碎了缸”。

界面先做可用灰盒，预留文本资源键和账号装扮接口；设置与装扮不进入房主存档。结算报告使用唯一 RunId，冻结通关瞬间投票集合，现场票与历史参与者称号分开。各人可先回大厅，但下一轮必须等待报告可靠保存且其余成员返回。

## 4 成本最高的事项和必须反馈的问题

1. 无缝主机迁移成本很高：需迁移刚体/约束/关卡机关、输入序列、投票和存档写权限。建议首版不做，使用已允许的会话结束降级；以后如改变目标单独立项。
2. 高延迟共享物理是主要实机风险。现输入走可靠顺序消息，断续网络可能积压陈旧输入；先测 RTT、丢包、输入年龄、快照间隔和抓取/跳跃响应，再决定输入通道与有限预测。不能仅调插值就保证联机无延迟，也不让各端独立裁定共享鱼缸结果。
3. 同一步四柱+危险优先是可实现但必须实证的底层改造。最高风险在回调时序、恢复接触、休眠与关卡几何，不是多写一个 if。
4. 可靠存档的成本在跨设备分叉、写入失败、重新挑战和结算中崩溃；五个按钮本身成本低。
5. 角色装扮内容尚未冻结，现阶段只预留接口与最小展示，不估算未知服装数量、商城或解锁系统。
6. 需求没有明显需要推翻的整体架构，但应明确双人开局是否取消、掉线继续与旧暂停方案的替换、伸缩是否正式启用。V1.1 中“真实停车”等历史用词不能重新引入停稳条件。
