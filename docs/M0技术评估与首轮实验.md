# 搬鱼缸 M0 技术评估与首轮实验

日期：2026-10-10。供两位程序和主策划讨论，负责人尚未分配。

后续进展：已新增带重力的本地交互测试场和 Windows 试玩版，编辑器与 Windows 各通过 24 项自动检查。操作与实现限制见 [M0试玩说明](M0试玩说明.md)，对应证据为 `docs/m0-evidence/carry-*.json`。下文保留首轮水平实验的原始范围和数据，不能与后续试玩验收混为一谈。

首轮 Unity 水平物理实验已执行，支持继续评估“动态角色代理＋鱼缸刚体＋有限抓取约束”路线。它仅验证水平运动的一小部分，不能证明完整搬运手感、悬挂、停车或异地联网成立。M0 仍在进行，尚未冻结生产架构和公共接口。

## 需求和环境基线

- Unity 6000.6.5f1，URP 17.6.0，Input System 1.20.0；MCP v10.3.0 固定提交。没有安装联网框架或 Steam SDK。
- 当前工程：`Unity/TankTogether`。本实验新增 Editor 工具，不修改 Main、构建列表、Packages 或 ProjectSettings；不新增正式关卡。
- 规则优先级：程序开工资料包 V12 中，已确认 D 清单高于补充规则，补充规则高于历史 V1.0；关卡 HTML 是任务书，不是完整布局。
- 不变的目标：只控制角色；底部自由抓取、抓取点固定；仅头顶支撑不主动水平驱动；正常拉扯不断抓；不自动扶正；危险接触即碎；真实停车激活检查点；四真人异地验收。

## 首轮实验的实现和限制

在 Unity Play 模式创建各自拥有独立 PhysicsScene 的临时场景，逐步执行真实 Unity 物理模拟，每组 200 步、每步 0.02 秒。测试后销毁实验对象并卸载场景，不保存临时场景，不推进主场景的模拟步骤。

候选结构：四个动态盒体代表角色，速度目标通过限力电机施加；ConfigurableJoint 将角色位置连接到鱼缸局部抓取点；鱼缸不直接接收人为平均后的四人方向。角色电机、碰撞和连接共同决定运动，连接不使用位置投影或张力断抓。

实验参数：鱼缸质量 20 kg、尺寸 3.5×0.5×2.3 m；角色代理质量 5 kg、盒体边长 0.4 m；目标速度 2 m/s，电机增益 110，单人最大驱动力 180 N；连接限制 0.12 m；鱼缸线性阻尼 0.8、角阻尼 2；求解迭代 12/4。全部是候选参数，不是策划定值。

**夹具简化必须保留在结论旁：**关闭重力、固定 Y 位置及鱼缸俯仰/横滚；角色和鱼缸之间关闭碰撞；阻挡物只阻挡角色，故不是正式危险墙；四个初始连接点只是测试输入，不是正式四角抓取槽。没有头部接触检测、鼠标抓取判定、自由换位重抓、第三人称镜头或可玩反馈。只适合筛查水平约束模型。

## 实测结果

Unity 6000.6.5f1 中八组场景、16 项诊断检查通过。原始结果随本报告保存在 `docs/m0-evidence/planar-physics.json`。下表数值取首次成功执行的数据，单位米、秒、度。

| 测试 | 4 秒结果 | 能支持的结论 |
|---|---|---|
| 四人同向 | 前进 7.454 m，峰值速度 1.930 m/s | 此水平夹具可以启动并保持移动 |
| 三顺一逆 | 前进 5.144 m，偏转约 -49.37° | 少数输入没有被忽略 |
| 两侧反向 | 偏转约 +89.92°，几乎不平移 | 偏心施力可产生转向 |
| 同样输入、镜像站位 | 偏转约 -89.92° | 转向来自施力位置，不只是输入平均 |
| 第 2 秒全部解除连接 | 松手后首步约 1.899 m/s，第 4 秒约 0.385 m/s | 解除连接保留惯性，阻尼随后减速 |
| 一人前方受阻 | 鱼缸前进 2.177 m，约 -114.70°偏转；受阻角色中心最大 z=0.882 m | 该阻挡会反向影响鱼缸，角色未越过墙前沿 |
| 无输入 | 位移 0 | 无输入时没有自发水平漂移 |
| 同向重复 | 与首次位移相同 | 同进程同参数可复现，不代表跨机器确定性 |

最大记录连接偏差约 0.145 m，高于设置的 0.12 m 限制，说明求解存在瞬态误差；本轮诊断上限为 0.30 m。是否允许这种误差，需要根据真实角色比例和视觉表现再评审。受阻时约 115° 的旋转也只能算“影响成立”，不能称手感舒服。

诊断阈值用于筛查爆炸、无效输入和无限拉长，不是 AT 验收门槛。所有组状态为有限数；鱼缸峰值速度低于 6 m/s、角色低于 8 m/s。实验没有测设备输入到画面的响应时间、真人手感或网络性能。

## 复现方法

1. 打开正式 Unity 工程，等待脚本编译完成。
2. 在干净的 Main 场景进入 Play 模式。
3. 运行菜单 `Tank Together > M0 > Run Planar Physics Probe`。
4. 查看 `Unity/TankTogether/Logs/m0-physics-probe.json` 的时间、16 项 checks 和实际采样值；菜单命令成功不等于测试通过。
5. 退出 Play 模式。Main 应仍为两个根对象、无未保存改动。

也可在项目总目录使用固定 MCP Python 环境依次执行：

```powershell
& 'D:/Tools/unity-mcp-v10.3.0/.venv/Scripts/python.exe' tools/m0-probe.py refresh
# 等待 Unity 编译完成再继续。
& 'D:/Tools/unity-mcp-v10.3.0/.venv/Scripts/python.exe' tools/m0-probe.py play
& 'D:/Tools/unity-mcp-v10.3.0/.venv/Scripts/python.exe' tools/m0-probe.py run
& 'D:/Tools/unity-mcp-v10.3.0/.venv/Scripts/python.exe' tools/m0-probe.py stop
```

工具每次列出实例并断言工程完整路径，run 检查新报告时间和每项结果。若实验失败也应执行 stop；不要在他人的未保存场景中启动。每次运行覆盖 Logs 下的临时报告，需比较的结果另存。

## 下一轮最小实验和停止条件

| 优先级 | 实验 | 观察证据 | 失败后的处理 |
|---|---|---|---|
| 1 | 恢复重力，加入实际头顶接触与自由底部抓取，验证松手换位 | 区分支撑/抓取；测滑动、偏差、穿透；游戏内显示真实状态 | 若纯刚体角色难以稳定，比较受控角色移动＋显式反约束，暂不扩大关卡 |
| 2 | 高低支撑、错时起跳、边缘有限悬挂 | 录像、角色与缸相对距离、角速度、救援路径，覆盖 F-04 | 不用自动扶正/正常断抓修饰失败，重新评估约束模型 |
| 3 | 四根安全支撑的驶入、停放与离开 | 四处承托数据、必要几何余量，覆盖 F-01/F-06 | 现有操作不成立时提交策划，不私加放下键或磁吸 |
| 并行优先 | 两个异地端共享一个运动物体，再接四真人 | 国内网络可达性、RTT/抖动、状态偏差、校正次数及录像 | 区分连接问题和模拟问题；评估预测或独立权威服务，不预设服务一定可用 |
| 网络定案前 | 主机进程突然退出 | 最后权威状态、抓取、速度、事件代次能否在新主机继续 | 若无法满足 D-08，提交成本/规则取舍，不能把普通客户端退出当成替代验证 |

## 网络方案和共同接口草案

候选路线：Steam Lobby 组织测试会话，Steam Networking/SDR 传输，支持对应传输适配的 Unity 框架处理消息与同步，一名玩家运行权威模拟。NGO 与 FishNet 仍需比较具体版本及适配器，不同时安装进正式工程。Steam 中继只传数据，不执行鱼缸物理；主机迁移需保存和恢复完整状态。独立服务可分离玩家和模拟宿主，但有部署成本且仍有服务故障问题。

先统一权威计算相关角色约束与共享鱼缸。客户端本地镜头独立；状态插值、操作预测与校正的范围依据实验决定。碰撞碎裂必须由权威端产生，不能由各端预测画面分别判死。

| 接口草案 | 最小字段或职责 |
|---|---|
| 输入命令 | PlayerId、序号、模拟 Tick、镜头水平朝向换算后的移动意图、奔跑/蹲下保持、跳跃与抓取/松手边沿；边沿不能因重发重复执行 |
| 抓取状态 | PlayerId、TankId、鱼缸局部锚点、状态版本、失败原因；仅权威端确认建立/解除 |
| 状态快照 | Tick、会话权威代次、RoundId、角色/鱼缸位置旋转与速度、抓取和支撑状态、检查点 |
| 游戏事件 | EventId、RoundId、Tick、事件种类/原因和相关对象；按代次排除旧局消息，按 ID 去重 |
| 模拟入口 | 固定步长读取各玩家命令，计算结果并产出快照/事件；网络层不得在任意回调中直接改 Rigidbody |
| 参数与日志 | 构建版本、参数版本、网络条件、输入和事件时间线，允许定位同一次碎缸在各端的表现 |

角色/鱼缸约束建议同一主要负责人整合；另一主要负责人负责网络和会话。模块归属由两位程序讨论，这张表不是已承诺的生产接口。早期联调前就对齐步进顺序，不等单机玩法完成再补网络。

## 需要策划和团队继续处理的事项

- F-02：掉线后再碎缸的在线角色复位集合；不得凭空复活离线角色。
- F-06/F-07：停车承托判据、是否须全员松键，以及停车和碎裂同时发生的顺序。
- F-09：确认断线前的卡顿过渡行为；重连后的回场规则。
- F-08/F-10：终点成功流程与死亡者归队路线，由关卡提案，依据真实运动能力验证。
- F-11：通过首轮真人录屏形成响应、稳定性、公平感的验收基线。
- F-12：选定联网框架后补测试房间创建/加入、准备、版本校验、退出和日志收集步骤。当前尚无可用联网会话，不将纸面流程写成已实现功能。

下一次可供试玩的最小目标是一套可调比例、一个安全支架、可区分支撑和抓取的本地实验场；暂不能测正式关卡、Steam 会话和四真人网络手感。
