## 玩家流程与网络职责

1. 房主启动游戏，读取账号下的共同进度，创建好友房间。
2. 房主使用“邀请 Steam 好友”；内部测试保留房间号作为备用入口。队友完成游戏连接后才计入人数，仅进入 Steam 房间不算准备完成。
3. 房间等待至少两人。房主发起从检查点开始，权威端重建本轮，等待各端接收新回合后进入可操作状态。
4. 任一队友中途加入或退出时，大家先暂停。房主重新确认成员后从最近有效检查点开始，不在空中直接增加人物或改变鱼缸负载。
5. 房主离开后本次会话结束。下次由同一房主创建房间读取进度；其他人另行建房使用自己的存档，不自动继承原房主进度。

Steam Lobby 用于组队和邀请，Steam Networking 传输连接数据，NGO 与应用协议负责连接和游戏消息；房主是角色、鱼缸、碰撞和进度事件的唯一权威。Valve 的邀请机制区分游戏已运行时的加入回调与未运行时的 `+connect_lobby` 启动入口，均需要游戏正确接入。[Steam Matchmaking & Lobbies 官方说明](https://partner.steamgames.com/doc/features/multiplayer/matchmaking)

当前仍用 App ID 480 做内部测试。正式邀请启动、游戏归属和发布路径需在自己的 App ID 下复验；当前不能承诺未启动游戏时点击邀请就能准确启动这份独立原型。收到邀请时已在别的会话中，不自动替玩家退房。

应用协议当前为 `tank-together-steam-04`。房间兼容性同时包含协议版本、物理配置签名、关卡标识、内容版本，以及两人辅助的三个实际参数；不同地图或参数的包不能混用。辅助参数通过 AssistSignature 按固定文化格式序列化，不能只比较配置资产签名而遗漏 Inspector 中的辅助数值。暂停、重开增加回合标识，并丢弃旧回合的输入和快照，避免旧抓取作用到重建后的鱼缸。角色控制权限仍由房主的连接与槽位映射决定。

## 两人适配的当前实验边界

按人数生成角色、允许两人开始，只解决了会话入口。两人能否完成移动、转向、跳跃、停车与整条关卡，必须另行验证。

当前动态人数模式采用临时负载方案：开局/检查点重开时冻结本轮人数 `SessionTeamSize`，鱼缸质量为基线质量乘以人数除以 4；基线 24 kg 时，两人 12 kg、三人 18 kg、四人 24 kg。搬运速度响应中的抓取比例也按本轮人数计算，松手不会触发即时减重。人物质量、地图和每人独立输入原则仍保留。

这是一套可替换的实现，不是策划冻结的“人数难度公式”。质量变化也会影响惯量、跳跃传力及救援；不能只测平地速度就宣称两人关卡平衡成立。人数变化先暂停并从检查点重建，避免搬运途中突变质量。

两人默认出生站位改为鱼缸局部前后排列：X=0，Z 分别为配置的前后半间距正负值；它仅定义初始位置，玩家仍可松手换位，不把抓取位置锁在两个点上。

第一次实际 Play 物理检查中，两人左右并排跳跃最大倾角约 **85.99°**，该项失败；同轮三人、四人的对应跳跃项通过，但只证明固定输入条件。证据为 `Unity/TankTogether/Logs/coop-session-physics-first-failure.json`，不能把“鱼缸尚未碎”当成两人手感合格。用户随后批准 COOP-20261013-05 的有限辅助，具体参数继续按实际试玩调整。

选中带 `M0CarryLab` 的对象，在 Inspector 的“两人联机抓握辅助（试调）”区域可配置下列公开字段；每项已有中文悬浮说明。这三项当前在组件上，不在 `M0CarryBaseline` 配置资产或原玩法参数窗口中。

| 字段 | 当前默认值 | 用途与限制 |
|---|---:|---|
| `twoPlayerGripSpring` | 160 | 按倾斜正弦施加趋向水平的有限恢复力矩；数值越大，越能抵抗轻微倾斜 |
| `twoPlayerGripDamping` | 18 | 抵消俯仰/侧倾的旋转速度，减少晃动；不直接抵消绕竖直轴的正常转向 |
| `twoPlayerGripMaxTorque` | 40 | 合力矩上限，单位 N·m；限制帮助强度，不构成保底救援 |

辅助同时要求 `DynamicRoster`、本轮人数为 2、有效抓取数为 2、倾角小于 45°。任意条件不满足就不添加辅助力矩；松手不会延迟保留辅助，达到或超过 45° 不靠它翻回。它通过物理力矩工作，不直接写鱼缸角度或位置；三人、四人和原本地四人实验不启用。辅助强度与前后站位的新组合仍需测横移、跳跃、松手、倾倒边界及回归，本文不将这些复验或双端真人体验写为通过。

## 保存什么、怎样恢复

存档底座为 `TankTogether.Networking.CoopCampaignSave`。房主账号与战役共同决定路径：

```text
Application.persistentDataPath/
  CoopCampaigns/
    <房主64位SteamID>/
      <campaignId>.json
      <campaignId>.json.bak
```

使用 Unity 实际返回的 `persistentDataPath`，不要将某台电脑的用户名或盘符写死。每个账号、每条战役当前保留一份主档及上一份有效备份。新建 API 只处理无档状态，不承担覆盖旧进度的“重新开始游戏”操作。

| 字段 | 含义与约束 |
|---|---|
| `schemaVersion` | 文件内进度结构版本，当前为 1；较新结构拒绝读取和覆盖 |
| `ownerSteamId` | 房主账号；文件内容必须与路径中的账号一致 |
| `campaignId` | 稳定战役标识，不能采用本次房间号 |
| `levelId` | 稳定路线/关卡标识，不能采用临时 Unity InstanceID |
| `checkpointId` | 会话目录中存在且合法的最近检查点标识 |
| `contentVersion` | 内容兼容版本；当前严格一致，不兼容时需显式迁移 |
| `revision` | 成功保存递增，用于拒绝旧缓存覆盖较新进度 |
| `savedAtUtc` | 写入时间，供核对与提示使用，不以时间戳代替合法性判断 |

不保存鱼缸或人物的任意现场坐标、速度、角速度、抓取关节、输入、NGO 连接 ID、Steam Lobby ID。恢复时由有效检查点定义重建安全支架、鱼缸与当前在线角色，清除旧运动和抓取，并建立新回合。退出时保留最后成功保存的检查点，不把半空、挂岸或刚碰碎的现场变成安全进度。

正式检查点接入后，持久保存必须发生在房主确认的合法激活事件中；客户端“我到了”不能推进存档。最近激活和最远解锁不是同一个概念，当前不额外加入选关解锁、跨房主合并或自动取更大关卡编号。

## 文件可靠性与异常处理

写入在同一目录生成唯一临时文件，刷盘并重新校验，再通过原子替换更新主档；原有效主档作为 `.bak`。内容有 SHA256 校验，保存前核对修订号，并用本地独占写锁保护读取修订号到替换的事务。`.lock` 文件可以保留；没有活跃独占句柄时它不表示锁住。

| 情况 | 当前结果 |
|---|---|
| 没有主档和备份 | 返回 `Missing`，可以显式 `Create` |
| 主档校验通过，版本/账号/检查点合法 | 返回 `Loaded` |
| 主档损坏或缺失，备份有效 | 返回 `RecoveredBackup` 并提示恢复来源；读取本身不修改原文件 |
| 从恢复出的备份继续保存 | 返回 `SavedAfterRecovery`；原损坏主档另存为 `.corrupt-*`，保留有效备份 |
| 主档与备份都坏 | 返回 `Corrupt`，不静默新建或回起点覆盖 |
| 主档或备份包含未来 schema | 返回 `FutureSchema`，旧程序不覆盖较新数据 |
| 内容版本不同 | 返回 `IncompatibleContent`，不偷偷选择旧备份；需要明确迁移规则 |
| 检查点不存在或不属于当前路线 | 返回 `UnknownCheckpoint`，不恢复到任意坐标 |
| 缓存 revision 过期 | 返回 `Conflict`，重新读取后再决定 |
| 目录无权限、写入失败、另一实例占写锁 | 返回 `IoError`，提示问题，不宣称保存成功 |

会话必须展示失败/备份恢复状态。当前存档失败会禁止继续并暂停；不能让用户误以为新进度已安全保存。文件校验用于识别损坏，不是商业级防作弊或不可篡改凭证。

## 程序与关卡策划的检查点契约

后续正式接入需要一个可验证的检查点目录。以下是接口约定，不代表这些组件已全部实现：

| 目录/事件项 | 责任与要求 |
|---|---|
| 稳定身份 | 程序与策划共同登记 campaignId、levelId、checkpointId、contentVersion；ID 在改名、移动场景物体后仍稳定，禁止重复和缺失 |
| 路线位置 | 策划给出连续路线中的合法顺序、具体停车点和回程路径；当前 CP0/1/2 只是待落地建议 |
| 鱼缸恢复姿态 | 每个点提供可验证的静止安全姿态及四根安全支撑引用；恢复后不能悬空、穿地或立即碰危险物 |
| 角色恢复位置 | 提供最多四个合法、不重叠、可走到鱼缸下方的出生位置；会话只使用在线成员所需位置，不生成缺席者 |
| 激活证据 | 房主验证四根真实支撑的有效承托，按 D-06 执行；经过区域、擦碰、悬空不触发。稳定阈值及是否必须松手仍需确认，不可暗加磁吸 |
| 单人死亡 | 在最近有效点重新生成该角色，并保留其他玩家和鱼缸状态；归队必须有合法路线，不默认为传送到缸边 |
| 激活事件 | 建议携带回合、权威 Tick、检查点 ID 和去重事件号；程序检查本轮有效性与重复事件，防止复位时安全摆放又重复激活 |
| 竞争事件 | 碎缸/危险接触与停车激活相近时，需有经确认的权威事件顺序；不要让过期客户端消息推进存档 |
| 内容迁移 | 删除/拆分检查点或改变路径兼容性时，提供旧 ID 到新 ID 的明确映射与验证；不识别则提示，不默认清档 |
| 终点 | 提供独立完成条件、反馈与后续行为；当前未保存“通关完成”标记，不能把抵达黄球视为已完成 |

存档 API 现有签名为：

```csharp
CoopCampaignSave.Load(ownerSteamId, campaignId, contentVersion, validateCheckpoint);
CoopCampaignSave.Create(ownerSteamId, campaignId, levelId, checkpointId,
    contentVersion, validateCheckpoint);
CoopCampaignSave.Save(progress, validateCheckpoint);
```

`validateCheckpoint` 为 `Func<CoopCampaignSave.Progress, bool>`。底座允许不传，但正式会话必须提供目录验证。它验证标识是否被当前内容接受；**不负责证明玩家刚才已经合法停车**，激活资格仍由房主的玩法流程判断。每次成功后使用返回的 `result.progress` 更新缓存，保留新的 revision。

接入正式激活时，先复制当前进度、填写合法 levelId/checkpointId，再提交保存并处理结果。当前 `SteamCarrySession.SaveCheckpoint(string)` 只支持实验 `start`，后续需要扩展为目录驱动并接收权威激活事件；不能仅放宽字符串白名单就宣称检查点系统完成。

## Steam Cloud 后续接入

当前只有房主本地持久进度，未接入 Steam Cloud。取得并配置自有 App ID 后，再选择 Auto-Cloud 或 Cloud API，配置文件路径、额度、同步规则并进行跨电脑与冲突测试。Valve 官方支持这两条路线，且要求保存路径区分当前 Steam 用户。[Steam Cloud 官方说明](https://partner.steamgames.com/doc/features/cloud)

项目拟只同步该房主账号下的正式进度及所需备份；临时文件、写锁、损坏留证和运行日志不自动纳入云同步。Steam Cloud 解决同一账号在不同电脑之间的文件同步，不自动把房主进度共享给所有队友，也不提供游戏物理主机迁移。这一节是后续配置计划，没有在 480 上替项目开通云存档。
