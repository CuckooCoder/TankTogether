# 《搬鱼缸》D-01～D-12 全量复核报告与遗留问题台账 V1.0

> 评审日期：2026-10-09｜适用范围：Unity 四真人首版原型（P0）及连续三段白盒（P1）  
> 依据：原《核心玩法程序需求策划案 V1.0》、原《核心交互规则补充 V1.11》、12 项主策划确认记录。  
> 本文的“发现/风险/建议”是复核判断，**不是新增的主策划已确认玩法**。需要更改玩家可见行为时必须另立规则决定。

## 1. 一句话结论

- **D-01～D-12：全部确认；允许冻结这些明确的选择。**
- **M0 技术评估和受控 M1 最小物理/联机实验：可正式开工。**
- **M2 真实异地四人联机：交付目标已定，但网络架构、权威端故障恢复及验收指标尚待 M0 评估，不能宣布技术已可行。**
- **M3 三段连续白盒：关卡布局与终点判定尚缺；不得称已具备按图施工的全量规格。**
- **整套策划规则/技术规格“完全冻结”：不通过。** 一部分影响实际玩法的未决边界仍存在；主策划需确认、程序需提供实测结果。

## 3. 确认过的“文档冲突”，已确定优先级

- **C-01｜检查点触发：** V1.0 §6.2/AT-23 原本以“通过检查点区域”作为激活条件；**以 D-06 停放并获得四点有效承托为准**，旧文字只作为历史记录保留。
- **C-02｜右键模式：** 较早的概念稿曾考虑右键切换，现按 D-05 **首版右键不承担抓取功能**。
- **C-03｜网络交付范围：** V1.0 §8.2 将本地/局域网/异地联机列作方案评估，现 D-09 要求 **M2 真正异地四真人**。
- **C-04｜抓取反馈：** 较早补充稿允许“可见反馈或调试信息”；D-12 明确 **必须有游戏内可见反馈**，调试日志不能替代。

上述四项属于**来源文字冲突已判明，不需要再讨论 A/B/C**；程序必须遵守后续明确确认的规则。

## 4. 未决问题：哪些会真正阻塞下一阶段

| 编号 | 严重程度 / 最迟解决阶段 | 已发现的问题与来源 | 不可擅自填写的答案 / 建议验证动作 |
|---|---|---|---|
| **F-01** | **高｜M2 检查点验收前** | D-06 要求四根安全支撑真实承托并激活；V1.0 §1.2 又把独立“主动放下/举起”功能列为 P2。**现有操作是否足以自然停放和驶离支架尚未证明。** | 程序先验证仅靠现有松手、头部承托、重力、位置和支架几何能否完成；不能就提出额外交互请求，由主策划确认，不得私加磁吸或自动摆正 |
| **F-02** | **高｜M2 掉线＋复位验收前** | D-08 一人断线后三人继续；V1.0 §6.4 写“将四名玩家恢复到最近检查点”。**断线后发生碎缸，不能凭空重生离线者。** | 建议区分“在线有效玩家集合”与“本局初始四人”；确认是否只对在线玩家复位。掉线者重连另立后续规则 |
| **F-03** | **高｜M0 架构评估阶段** | D-08 要求掉线后其余玩家继续，但若掉线者本身是鱼缸/会话的**权威计算宿主**，可能整局丢失。 | 程序必须对比权威服务独立托管、主机迁移或其他可靠方案，并展示会话/物理状态如何继续；M2 必须测试关键权威端故障路径或明确经主策划批准的交付例外 |
| **F-04** | **高｜M1 悬挂原型前** | D-02 正常受拉不脱手、D-03 允许踩空悬挂、D-04 鱼缸可带动角色、V1.0 §3.3 抓取点固定且不能无限伸长。**玩家坠下时不能既无限下落又保持定长抓取。** | 程序展示一种不会穿模/弹飞的有限悬挂方案，含边缘地形阻挡、能否通过正常操作回到平台；不得偷偷把普通踩空改成自动松手 |
| **F-05** | **高｜M2 接触判定验收前** | D-07 无玩法容错且“真实可见接触即碎”；D-09 异地四端共享但网络插值导致各端看到的位置略有差别。**‘四端画面都在同一帧看到接触’不能未经验证就保证。** | 采用单一权威碰撞结果并记录碰撞对象、位置、时刻，审查延迟下的客户端表现、校正和可解释提示；若不可避免的画面歧义影响公平，需要单独评审，不得私自改成撞击力度阈值 |
| **F-06** | **高｜M2 停车点验收前** | D-06 规定“四处有效承托”，但停稳程度、四点识别、是否松开左键尚未确认。仅凭碰撞传感器接触可能因微小弹跳不停切换状态。 | 程序展示明确、可观察、稳定的候选停车判据；任何必须松左键、自动吸附、额外停靠键，均需主策划另行批准；不将技术去抖误认为玩法停稳时间 |
| **F-07** | **中｜M2 复位验收前** | 同一近似时刻发生危险碰撞与停车激活，或断线与复位；原 V1.0 只要求一致性，没冻结事件优先级。 | 程序提出事件优先级与权威时间线；建议原则是不可通过临死一刻的滞后消息偷激活存档，具体先后需评审并做测试 |
| **F-08** | **中｜M3 白盒制作前** | V1.0 第 7、13 节列出三段白盒能力，但没有具体终点位置、通关触发、通关反馈、结束/重试流程和完整空间结构。 | 单独《三段白盒关卡策划案》补上首尾、路径、尺寸调整范围、检查点位置和终点触发；此项不是 M0 阻塞 |
| **F-09** | **中｜M2 掉线验收前** | D-08 确认断线后的行为已定，但“短暂网络卡顿→确认断线”转换中，角色仍施力还是冻结、通知与重连行为未定。 | 程序给出断线检测和过渡状态，主策划确认对玩家可见的过渡行为；不强制首版完整断线重连产品化 |
| **F-10** | **中｜M3 三段关卡整合前** | 玩家单独在最近检查点重生，而鱼缸和其他玩家仍在前方；部分地形可能没有实际返回路线。 | 由关卡策划确保回程/追赶路径存在，或提出新规则变更；不能偷偷将死者传送到鱼缸旁 |
| **F-11** | **中｜M1/M2 验收前** | V1.0 对“灵敏、稳定、不频繁错误”有明确体验目标，但尚无实测数据或量化基线。 | 程序提供可测指标：输入响应、同步偏差、非法接触、复位重复率、手感录屏；首轮实测形成基线，主策划审核具体验收标准，不凭空设参数 |
| **F-12** | **中｜M0 开工方案时** | 缺少最简“四人如何创建/进入同一测试会话、准备/开始、退出、记录构建版本”的交接操作说明。 | 可以采用最小测试入口与连接说明，不要求正式大厅；程序在 M0 回填测试启动/故障恢复/日志操作步骤 |

**优先先处理 F-01～F-05**；其中 F-03 属于最早应由程序回答的体系结构问题。F-08 在三段白盒前再落实。

## 6. 建议程序回填的最小问题集

1. 现有交互如何真正把鱼缸放到四根棉花安全支撑上、再从支架离开？请提供演示或低成本实验证据。
2. D-02/03/04 组合下如何限制人物和鱼缸的位置、允许悬挂并避免无限拉长/穿墙/物理爆炸？
3. 谁对多人共享鱼缸的最终结果有权威？普通玩家断线和权威宿主断线是否都能按 D-08 继续？
4. 断线后游戏人数从四变三，危险碰撞后全队复位怎样处理？请给规则建议，**不能未经主策划同意直接生效**。
5. 真实危险接触的权威判定、可见玻璃边缘与联网延迟之间，如何减少玩家不能理解的碎缸？
6. D-12 三种状态如何让普通玩家不看日志也区分？
7. 近似同时发生停车成功与危险碰撞，如何确定最终检查点与复位目标？
8. M2 四名真人跨网络进入测试场景的最小流程是什么？

## 7. 明确不应误称为“已完成”的事项

- **不等于原型已验证好玩。** 有戏剧效果与操作乐趣需要四人试玩、观察与迭代；策划文档不能代替试玩。
- **不等于纯物理方案必然能稳定联网。** 程序仍需评估可控物理、混合方案与权威同步。
- **不等于 D-06 停车入位已经可由现有按键实现。** 仅设计目标已确定，尚需证明可玩性。
- **不等于所有规则无歧义。** F-01～F-12 中仍有需要策划确认或程序证明的内容。
