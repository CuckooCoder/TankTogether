# 《搬鱼缸》核心玩法程序需求策划案 V1.0

> **文档性质：** 首版四人可玩原型的游戏策划需求（Markdown）  
> **阅读对象：** 程序团队；主策划、关卡策划可用于需求和验收对齐  
> **项目引擎：** Unity  
> **文档状态：** 核心行为规则已冻结；物理参数和网络方案待技术评估、原型验证  
> **制定日期：** 2026-10-09  
> **优先级标识：** P0 = 首版不可缺少；P1 = 三关试玩所需；P2 = 暂不进入首版

---

## 0. 阅读须知：怎样理解这份需求

这是一份**描述玩家操作、系统响应、状态规则和验收结果**的策划案，**不是程序实现方案**。

- **必须遵守（已确认）**：玩家操作逻辑、鱼缸与角色之间的基本关系、失败与重生原则，以及首版范围。
- **实现方式自主评估**：程序自行决定角色控制器、刚体/约束/自定义受力算法、多人联网框架、数据同步及代码架构；两名程序如何分工由程序团队自行安排。
- **需原型验证**：重量、速度、惯性、力矩、碰撞容差、跳跃力度、蹲下牵引、镜头参数等。不得把本文件中的体验描述误解成已经确定的物理数值。
- **建议默认、可评审修改**：为避免原型中断而提出的调试和极端状态处理；这些并非用户已确认的长期正式玩法。
- **如发生冲突**：以“已确认核心规则”优先；程序发现某条规则无法低成本稳定实现时，应提出复现案例、影响和备选方案，由主策划确认是否修改，不得自行悄悄改变核心交互。

### 0.1 一句话玩法

四名玩家扮演小偷，共同从下方托住并搬运一个巨大、脆弱的鱼缸，沿连续路线逃离。每人只能控制自己的角色，但每个人的行动都会影响同一个鱼缸；鱼缸接触危险环境就碎裂，所有人回到最近检查点。

### 0.2 原型成功的定义

四名真人在同一测试会话内能稳定抓取、托住、移动、转弯、跳跃和救援鱼缸，能完成连续的三段白盒路线；且多数失败由玩家可理解的操作或环境接触引起，而不是物理异常或同步错误。

**体验优先级：** 输入响应和可控性 > 受力反馈的清晰度 > 适度重量感与惯性 > 物理真实性。困难应主要来自多人协作与环境，而非迟钝、随机、不可解释的操控。

## 1. 开发范围与交付边界

### 1.1 首版目标（P0 / P1）

| 项目 | 首版要求 | 优先级 |
|---|---|---|
| 引擎 | Unity；具体版本由程序选择并统一 | P0 |
| 测试人数 | **固定 4 名真人玩家**；可在程序选择的测试连接方案中同时控制各自角色 | P0 |
| 玩家 | 4 个独立角色，第三人称移动、跳跃、蹲下、抓取；彼此有实体碰撞 | P0 |
| 鱼缸 | 1 个共享的透明玻璃鱼缸实体；拥有体积、受力、惯性、倾斜、碰撞 | P0 |
| 抓取/支撑 | 头顶支撑与左键抓取是不同状态，均可与鱼缸交互 | P0 |
| 多人施力 | 根据有效抓取者的位置和操作综合决定鱼缸运动 | P0 |
| 失败重生 | 危险碰撞碎缸；玩家坠落单独重生；最近检查点复位 | P0 |
| 测试环境 | 平地核心交互试验场 | P0 |
| 三关白盒 | 一条连续路线，依次验证基础搬运、连续转弯、合作跳跃 | P1 |
| 调试/观测 | 关键状态、碰撞原因、重置事件和核心物理参数可观测、可调整 | P0 |

**特别说明：** 不要求策划规定具体到个人的任务拆分。程序团队自行组织实现，但应保证需求接口、测试版本和问题反馈可追踪。

### 1.2 首版明确不制作（P2）

- 鱼缸从地上被人物举起、主动放下、投掷、翻滚或侧面牵引。
- 鱼缸扔入河流、随水漂流、从另一地点重新取回等中后期机制。
- 水、鱼以及内部液体动态对重心/惯性的额外影响。
- 人物体型变化、风力、传送装置、复杂机关、正式大章节、剧情演出。
- 2–3 人完整平衡适配、AI 队友、匹配/大厅/公开服务器等长期功能。
- 正式画面、精细动画、完整音效、商业化及存档系统。

上述事项可以在设计上保留扩展可能，但**不得成为首版 P0 阻塞项**。

## 2. 玩家操作规范（P0）

### 2.1 输入表

| 输入 | 行为 | 已确认约束 |
|---|---|---|
| W / A / S / D | 角色平面移动 | 相对角色**摄像机的水平朝向**决定移动意图；旋转镜头本身不直接推动或旋转鱼缸 |
| 鼠标移动 | 调整第三人称镜头 | 四人镜头独立；镜头变化不等于鱼缸运动 |
| Shift（长按） | 奔跑 | 抓取时仍允许输入奔跑意图，但实际运动受鱼缸及队友约束 |
| Space | 跳跃 | 角色跳跃可以通过头顶支撑产生向上顶升；抓取时传力更稳定 |
| Ctrl（长按） | 蹲下 | 未抓取时降低头部支撑高度；抓取时对该抓取位置产生有限向下牵引 |
| 鼠标左键（长按） | 抓取 | **只有底部有效范围内才能抓取**；松开左键立即解除主动抓取关系 |

**首版不加入右键切换抓取模式。** 鼠标滚轮镜头缩放如程序认为有必要，可列为易实现的可选镜头功能；不是当前核心验收的硬门槛。

### 2.2 操作一致性要求

1. 玩家只直接控制自己的角色，**不存在直接控制鱼缸前进/转向/扶正的独立按键**。
2. 玩家输入产生的是**运动意图**，并不保证角色或鱼缸一定达到期望位置：例如受队友拉扯、墙体或鱼缸约束时，实际位移可以变小。
3. 普通移动应有迅速、清晰的响应；不可为了表现重量而强制增加明显输入延迟。
4. 被鱼缸阻挡或限制时，应能从角色实际运动及鱼缸反馈判断原因；不可出现无法解释的瞬移、弹飞、持续振荡。

## 3. 鱼缸与角色的基本关系（P0）

### 3.1 鱼缸定位

- 鱼缸是一个**共享、具有实体碰撞体积的物体**，不是角色头顶的固定动画附件。
- 鱼缸正常搬运时位于角色头顶附近，由玩家/安全支撑物在下方承托；**不具有永久反重力悬浮功能**。
- 鱼缸本体随四人有效施力、惯性、重力、支撑和环境约束改变位置、角度和速度。
- 首版默认一个鱼缸、四个角色；不实现多鱼缸互动。

### 3.2 两类核心交互——务必分开

| 状态 | 生效条件 | 允许的主动行为 | 不允许的行为 |
|---|---|---|---|
| **未抓取，但头部支撑** | 头部处于鱼缸底部有效接触区域，存在实际承托接触 | 提供向上的垂直支撑；头顶上升可顶起鱼缸；根据头部高度变化影响承托 | **不能通过 WASD 主动给鱼缸提供水平搬运动力**；不会自动随鱼缸水平移动 |
| **已抓取** | 角色位于底部有效抓取区域，按住鼠标左键且建立抓取关系 | WASD 产生搬运水平驱动；跳跃产生更稳定的垂直传力；蹲下产生有限向下牵引；通过移动纠偏 | 不可隔空抓取、无限离开抓取点、从侧面牵引；不得独占鱼缸的控制权 |
| **离开接触且未抓取** | 无头部有效接触，也无抓取关系 | 自由移动、重新靠近并抓取 | 不提供支撑或驱动力 |

> **力学语义：** “不主动产生水平驱动力”不等于关闭所有碰撞反作用。程序可自行处理被动接触造成的阻挡，但不能让未抓取者仅凭 WASD 实际拥有与已抓取者等同的主动搬运能力。

### 3.3 抓取点规则

1. 鱼缸**底部任意有效位置**允许建立抓取；不将四名玩家强制固定为四角站位。
2. 玩家抓住后，抓取点**相对鱼缸局部空间固定**；玩家不可保持左键按住的同时，让抓取点无成本地沿底面自由滑动。
3. 换抓取位置需先松开左键、移动到新位置、再次按住左键。
4. 已抓取状态下，人物和抓取点之间允许有限的弹性/容差，但人物不可自行远离且仍保持远距离抓取。
5. 如果玩家前进但鱼缸被其他玩家/环境阻挡，其角色实际移动也受到约束，不能出现“角色走远、鱼缸原地不动、连接被无限拉长”的现象。
6. 有效抓取范围、约束算法和可允许误差由程序提出方案并在原型中调整。

### 3.4 推荐的功能状态划分（逻辑要求，不强制代码结构）

- **Free（自由）**：无抓取；可以自由行走；若头部接触鱼缸底部则进入“头顶支撑”行为。
- **Supporting（仅支撑）**：未抓取但正在承托鱼缸，能顶住和向上顶升，不能主动水平驱动。
- **Gripping（抓取）**：已从底部有效位置建立抓取，承担主动搬运与受限移动。
- **Falling/Respawning（坠落/重生）**：角色离开有效区域触发重生流程；抓取关系终止。

Supporting 可由碰撞持续检测产生，不要求一定成为独立代码枚举。重点是**外在行为正确**。

## 4. 核心物理运动要求（P0）

### 4.1 四人共同施力

- 每名**有效抓取者**的移动方向、实际抓取位置以及相关上下运动，都应对鱼缸运动产生作用。
- 系统综合多个玩家的作用，决定鱼缸的**水平平移、水平朝向变化、垂直运动、俯仰/横滚倾斜**。
- 同样的移动方向，施力点分布不同，可以产生不同的旋转/偏转效果。
- **不能简单套用“多数人绝对控制”或“意见不一致就完全锁死”的规则**；少数玩家仍应有可感知的影响力。
- 鱼缸的平移、旋转、倾斜均应可以被玩家通过动作理解和预判，不追求不可控的“绝对真实”。

#### 典型行为预期

| 场景 | 应表现为 | 不应表现为 |
|---|---|---|
| 4 人一致向前 | 平稳、迅速地开始移动，有一定重量反馈 | 明显延迟、无法启动、突然加速爆冲 |
| 4 人一致停止 | 减速明显，但允许小幅惯性 | 瞬间完全无惯性，或持续长距离滑行不可控 |
| 3 人向前，1 人后退 | 综合成前进阻力和/或偏转，结果受抓取位置影响 | 后退者输入完全无效，或物体突然剧烈弹飞 |
| 左右玩家反向移动 | 可能产生转向/旋转 | 仅按四个输入平均导致始终无法旋转 |
| 某位玩家被队友或地形阻挡 | 鱼缸发生合理受阻、偏转或减速 | 玩家穿模、持续压缩导致鱼缸乱飞 |

### 4.2 重量感、惯性与控制响应

**已确定的手感方向：** “有重量，但仍然灵活”，且用户明确要求“非常可控、手感好、舒服、灵敏”。

策划侧期望：

1. 玩家移动、停止、转向时，鱼缸应**及时响应**。
2. 通过小幅惯性、多人运动冲突和失去支撑后的失衡表现重量，而非通过严重操作延迟。
3. 四人全部松开左键后，鱼缸**不立即抹除水平速度**，而是在剩余惯性、阻尼、支撑和环境作用下继续运动或渐渐减速。
4. 未抓取但头部仍接触鱼缸的玩家不会自动被鱼缸带走，必须自行移动以跟上它。
5. 允许适当的线性/角度阻尼，抑制不必要的长时间振荡。
6. 若多人主动施力的结果与鱼缸既有速度相反，鱼缸应按有效施力逐渐改变速度，而不是无因突变。

### 4.3 自动稳定与主动救援

- **禁止**系统在没有有效恢复性受力的情况下，仅因“鱼缸倾斜”而主动把它转回水平。
- **允许**旋转阻尼降低角速度；允许重力、实际头部支撑、抓取点施力自然造成恢复或继续失衡。
- 玩家通过调整站位、抓紧、跳跃、蹲下及平面移动，可以主动对鱼缸施加纠偏影响。
- **鱼缸倾斜本身不立即失败**；危险可读，玩家应有机会救援。最终接触危险环境时才判定碎裂。
- 不保证任何角度均可被少人救回：当所需纠偏超出当前玩家有效施力能力时，必须依靠队友。

### 4.4 单人 / 少人临时搬运

- 在四人测试局中，允许出现只有 1–3 人仍在鱼缸下方支撑或抓取的临时局面。
- 一人在鱼缸重心附近抓紧、站位合理时，可以**极慢移动**并尝试小幅纠偏，能力显著低于多人。
- 不要求一人能够从严重失衡状态必然救回鱼缸。
- 不使用“必须至少 N 人抓住鱼缸才允许运动”的生硬人数开关。
- **注意：** 这不等于首版必须完整实现 1–3 人开局的关卡/难度适配；首版仍固定 4 名真人。

### 4.5 跳跃与蹲下

**跳跃：**

- 非抓取状态：玩家跳跃时，如果头部产生有效接触，可向上顶升鱼缸；若尚未碰到鱼缸，不能隔空施力。
- 抓取状态：向上运动对鱼缸的传递更稳定、可控。
- 四人同步跳跃时，鱼缸应相对稳定升高；错时跳跃可因各点受力不同导致倾斜。
- 不设置“四人必须同一帧按 Space 鱼缸才跳”的隐藏硬判定。

**蹲下：**

- 非抓取状态：头部降低，仅减少/失去原有向上支撑；不能凭空主动向下拉鱼缸。
- 抓取状态：蹲下可以对所抓住的鱼缸底部位置施加**有限**向下牵引。
- 两侧不同动作可能引起倾斜，但不得直接将某侧强制插值到玩家头顶高度，忽略其他抓取者和物体受力。

## 5. 角色实体碰撞、环境碰撞与风险控制（P0）

### 5.1 角色之间

- 四个玩家具有实体碰撞，会相互阻挡；该规则是玩法的一部分。
- 玩家碰撞必须尽量表现为可信的阻挡与滑动，而不是积累异常冲量、瞬间弹飞或穿模。
- 抓取约束、玩家碰撞和地形阻挡同时发生时，系统要避免无法解除的持续性物理死锁。
- 具体角色控制架构、碰撞体大小、推挤规则由程序试验；不得为图方便直接取消全部玩家实体碰撞。

### 5.2 鱼缸与接触对象分类

| 对象 | 是否可触发碎裂 | 规则性质 |
|---|---|---|
| 危险墙壁、地面、天花板、硬质场景物体 | **是**，有效危险接触即碎 | 核心规则延伸；具体对象由关卡标记 |
| 检查点四根柔软支撑柱 | **否**，允许安全承托 | 已确认例外 |
| 玩家头部/合法支撑或抓取接触 | **否**，必须正常工作 | 基础玩法所必需 |
| 其他非头部角色接触 | 不直接作为“危险环境”触发碎裂；其物理阻挡/力学影响需验证 | 原型建议，不允许借此获得与抓取等效的侧面搬运能力 |
| 其他后续特殊安全物体 | 首版不默认添加；如新增须显式标记 | 待扩展 |

**碰撞原则：** 玩家看见鱼缸实际触碰危险物时，应能理解失败原因。不能依赖网络抖动、微小穿透、物理噪声触发大量“看上去没碰到却碎了”的情况。

程序应提供明确的接触分类机制（碰撞层、标签或其他等效方案），并能够记录**导致碎裂的具体接触对象及位置**。

### 5.3 地图边界异常（原型建议默认）

- 鱼缸掉出有效游戏区域、长时间无法恢复或落入无碰撞深渊时，允许触发全队失败/复位，避免软锁。
- 研发测试版本提供**手动重置到最近检查点**的调试命令。
- 上述机制是工程兜底，不是希望正式玩法频繁替玩家解决失误。

## 6. 初始摆放、检查点、死亡与重生（P0）

### 6.1 初始状态

- 开始或全队失败复位时，**鱼缸已位于头顶高度，被四根柔软支撑柱托住**；不是在地面等待玩家举起。
- 四名玩家出生在该检查点附近的合理位置，可以自行走入鱼缸下方。
- 玩家进入有效区域后，可以直接按住左键建立抓取并开始搬运。
- 支撑柱本身不能触发鱼缸破碎；几何形状/碰撞设计不应阻碍玩家进入下方或鱼缸离开支架。
- 不要求四名玩家在开局第一帧就处于抓取状态。

### 6.2 检查点激活

- 只有**鱼缸本体**通过关卡策划配置的有效检查点区域，才可激活检查点。
- 玩家单独跑到前方、穿过触发区域、摔落到附近，都**不能**激活检查点。
- 最新激活的检查点成为所有后续重生和鱼缸碎裂后的复位目标。
- “鱼缸通过”的判定边界（鱼缸主体通过、中心通过或完整穿过触发面）由程序与关卡策划共同提出可读、稳定的判定方案；需要避免鱼缸只擦到触发器边缘就错误激活。
- 检查点在初版可使用简单触发体与调试提示，不要求正式视觉特效。

### 6.3 玩家坠落与单独重生

- 玩家跌落/进入角色死亡区：该玩家终止当前抓取和支撑，在**最近已激活检查点**的预设出生点重生。
- 鱼缸和其他仍存活玩家继续当前游戏状态，**不因为单人死亡而自动传送或重置**。
- 坠落前已经造成的鱼缸速度、倾斜、受力结果，不应被无条件回滚。
- 重生后玩家处于普通自由状态，**不会自动恢复抓取**；必须返回鱼缸下方重新抓取。
- 不将玩家直接传送到当前鱼缸旁边。关卡回程距离由后续关卡策划负责。

### 6.4 鱼缸破碎与全队复位

**触发：** 鱼缸与有效危险环境发生接触；地图外异常兜底可按 §5.3 触发。

**结果：**

1. 立即进入鱼缸失败状态，停止正常搬运输入对该轮结果的影响。
2. 向所有玩家反馈鱼缸破碎/全队失败（首版允许临时文字或简单效果）。
3. 将四名玩家恢复至最近检查点的合理出生位置。
4. 将鱼缸恢复为检查点支撑柱上、可重新抓取的初始安全状态。
5. 清除上轮残留速度、角速度、抓取连接与未完成物理状态，避免复活瞬间二次破碎。
6. 新一轮开始后，玩家仍需自行进入鱼缸下方建立抓取。

**实现注意：** 网络环境下，碎裂、检查点激活、复位和抓取状态要有一致的最终结果；判定权归属由程序自主评估并统一设计。

## 7. 首版连续三段白盒与程序接口（P1）

**此处仅定义程序需要支持的基础关卡能力；具体路线、障碍尺寸、难度节奏由下一份《关卡策划案》定义。**

| 小关卡 | 验证的核心行为 | 程序需要支持的内容 |
|---|---|---|
| 第一段：基础搬运 | 四人靠近、抓取、平地搬运、启停、换位、抢救 | 平面运动、头部支撑、抓取/松手、惯性、安全初始支架 |
| 第二段：连续转弯 | L 型及连续拐角中的多人协调、转向与边缘碰撞 | 鱼缸旋转、抓取点偏心施力、危险墙壁接触判定 |
| 第三段：合作跳跃 | 同步/错时跳跃、空中倾斜、落点与补救 | 角色跳跃、顶升和抓取传力、空中/落地碰撞与死亡区 |

- 鱼缸安全初始点和支撑柱位置。
- 玩家出生点及角色死亡/坠落区域。
- 鱼缸危险碰撞体、安全承托碰撞体。
- 检查点区域、激活条件和复位目的地。
- 基础地形碰撞和关卡衔接。

暂时不要求程序为三关开发专用机关或一次性脚本解法。三关应优先复用同一套物理交互系统。

## 8. 四人联机及系统一致性要求（P0）

联机的具体产品形态和网络方案由两名程序自行评估。**但首版内测的验收对象是四名真人共同操作同一个鱼缸，不是四个本地脚本角色的演示。**

### 8.1 体验要求

1. 四个客户端/玩家会话中，玩家能够看到**同一个共享鱼缸**的连贯运动状态。
2. 同一时刻不会出现各玩家分别控制自己版本鱼缸、最终状态互相冲突的结果。
3. 抓取/松手、当前有效抓取点、头部支撑、角色坠落、检查点激活、鱼缸碎裂和复位，必须在多人测试中有一致结果。
4. 常见网络波动下不能频繁发生瞬移、物理爆炸、反复碎裂、无法抓取或错误激活检查点。
5. 程序需明确：共享鱼缸运动由何处最终计算/确认，输入如何传递，角色与鱼缸的状态如何同步，以及如何排查延迟造成的问题。

### 8.2 技术评估项（不指定方案）

- 测试环境采用本地多实例、局域网、异地联机或其他方案，交付阶段分别覆盖哪些条件。
- 角色移动与鱼缸受力如何共同参与网络更新；何处是最终权威状态。
- 玩家抓取位置和支撑接触如何同步，避免各端判定不一致。
- 延迟/抖动/丢包条件下的校正策略及其对手感的影响。
- 异常断线或掉线在首版如何处理。**此处尚无策划确认的正式玩法规则，程序先提出不会阻塞内部测试的临时测试策略即可。**

**建议：** 单机/本地实验场可以先用于手感试验，但多人状态一致性必须尽早开展技术试验，不应等三关白盒全部完成后才处理。

## 9. 参数化与调试需求（P0）

程序无需在首次实现时给出最终数值，但**关键参数必须方便修改**，避免每次调手感都要改动大量代码。

| 参数组 | 建议可调参数方向 | 最终确认方式 |
|---|---|---|
| 角色平面运动 | 自由移动/抓取时速度、加减速、奔跑系数 | 四人实机体验 |
| 鱼缸平移 | 施力响应、最大速度、线性阻尼、松手惯性 | 平地启停测试 |
| 鱼缸旋转 | 转向响应、角速度范围、角阻尼 | 双人反向/连续转弯测试 |
| 抓取 | 底部检测区域、位置限制、施力强度、约束容差 | 松手换位、多人拉扯测试 |
| 头顶支撑 | 有效接触区、支撑传力、接触恢复与脱离条件 | 未抓取支撑测试 |
| 跳跃 | 起跳速度、顶升力、抓取传力比例 | 同步/错时跳跃测试 |
| 蹲下 | 高度变化、下降速率、有限牵引力 | 单侧蹲下失衡测试 |
| 稳定性 | 旋转阻尼、可控的速度/力限制（不等于自动扶正） | 救援与极端输入测试 |
| 碰撞 | 有效接触判定、误差处理、角色滑动/阻挡参数 | 低速贴墙及拥挤测试 |
| 镜头 | 距离、高度、跟随/遮挡行为 | 鱼缸边缘及路面可见性测试 |

**建议最低调试信息：**

- 每名玩家：自由/支撑/抓取/重生状态、当前抓取点是否有效、当前输入意图。
- 鱼缸：位置、速度、角速度、倾斜、当前抓取者数量和有效支撑者数量。
- 碰撞：最近一次触发碎裂的物体、碰撞位置、触发时间。
- 流程：当前检查点编号、激活事件、失败事件、复位事件。
- 多人：至少可以观察鱼缸状态偏差、抓取状态不同步或明显校正事件。

首版调试界面可很简陋，只要能帮助程序和策划定位问题即可。

| AT-24 | P0 | 鱼缸破碎后全队复位 | 全队与鱼缸回最新检查点，鱼缸在安全支撑柱上；速度/抓取残留清除 |
| AT-25 | P0 | 四名真人同时抓取、松开、撞墙、复位 | 多人均看到一致的核心事件；不出现不同步导致的双重状态 |
| AT-26 | P1 | 游玩连续三段白盒 | 基础搬运、转弯、跳跃皆可正常触发核心机制并完成流程 |

### 10.1 体验级验收（必须有真实试玩记录）

以下不宜假装能够通过单元测试直接证明：

- **灵敏：** 玩家操作后能迅速看到合理反应，没有明显输入迟钝感。
- **可理解：** 玩家在失败后通常知道是碰墙、失去支撑、操作不一致，还是自己站位有问题。
- **可救援：** 至少有一部分中度倾斜能靠玩家实际操作救回，而不是失衡后只能等死。
- **有协作：** 四个人的行动确实影响同一个鱼缸，需要交流与协调。
- **有事故：** 在白盒里就能发生可理解、可复述的失误、救援与团队争执，而非仅靠画面包装。
- **能复玩：** 失败重开后玩家愿意再次尝试，且失败大多被认为合理。

具体成功率、耗时、失误密度需在首轮测试形成基线，不提前用无依据的数值作为硬性验收门槛。

## 13. 与下一份《关卡策划案》的接口

本文件只规定系统能力，不规定具体关卡长度、路线尺寸、宽度与障碍摆放。下一份关卡策划案应基于已经确定的物理能力，提供：

1. 连续三段路线的平面结构与衔接方式：基础搬运 → 连续转弯 → 合作跳跃。
2. 各段要训练/验证的操作和想产生的典型协作事故。
3. 可调关卡尺寸：鱼缸与通道间隙、转弯半径、平台间距、高差等（以 Unity 实测后定稿）。
4. 检查点的具体位置、柔软支撑柱布局、玩家出生位置和坠落回程路线。
5. 每类障碍的危险碰撞区域、安全支撑区域及过关判定。
6. 首次试玩的观察方法：是否看懂、何处卡住、是否产生沟通和救援。

**强制衔接原则：** 如果白盒设计必须新增某个核心物理能力（例如特殊攀爬、投掷、自动拾起），不得默默作为关卡需求塞给程序，需先由主策划评估是否进入当前版本。

## 15. 最终执行原则

1. **先证明核心搬运手感，再扩大关卡内容。**
2. **四人可以共同影响鱼缸，但无人拥有单独的“鱼缸方向盘”。**
3. **鱼缸不自动扶正，允许阻尼；玩家的操作承担真正的纠偏责任。**
4. **玩家的自由支撑、主动抓取和危险接触必须明确区分。**
5. **物理真实感为可控性服务，不为真实而牺牲游玩体验。**
6. **程序自行选择技术实现与团队分工，主策划负责玩法验收和规则变更。**
7. **没有四真人稳定原型，就不视为核心系统已经验证完成。**
