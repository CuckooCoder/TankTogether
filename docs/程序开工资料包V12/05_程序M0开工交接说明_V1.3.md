# 《搬鱼缸》程序团队 M0 开工交接说明 V1.3

> **性质**：可直接发给两名程序的第一轮任务说明，**仅针对技术评估与最小试验方案**，不表示整款游戏的全部需求已经冻结。  
> **日期**：2026-10-09

## 1. 项目目标（请优先看这一段）

我们要制作 Unity 的第三人称四人合作搬运游戏首版可玩原型：四名真人通过各自的移动、抓取、松手、跳跃与蹲下，共同影响一个有体积、惯性和倾斜的脆弱鱼缸。鱼缸与危险环境接触即碎，全队回检查点；单人坠落则仅本人重生。

**第一阶段的首要目标**不是三关完整可玩，也不是画面，而是证明：**多人抓取 + 角色受限 + 鱼缸运动 + 联机共享状态，能够稳定且可控地工作。**

**交接附件**：

1. 《搬鱼缸》核心玩法程序需求策划案 V1.0（需求主文件）。
2. 《搬鱼缸》核心交互规则补充与决策清单 V1.12（D-01～D-12 已确认，关键边界仍待评审）。
3. 《搬鱼缸》核心玩法规则确认清单 V1.0（D-01～D-12 已确认）。
4. 《搬鱼缸》全量复核报告与遗留问题台账 V1.0（先看尚未冻结边界）。
5. 本说明（M0 阶段交付要求）。

## 2. 本次 M0 请交付什么

| 交付项 | 具体内容 | 最低合格标准 |
|---|---|---|
| 技术选型 | Unity 版本与基本运行环境；角色控制、鱼缸受力/约束的候选实现；联网方案 | 各项可解释，主要风险可验证，不需要写长论文 |
| 四人施力试验思路 | 如何从多人的输入与抓取点位置形成可控的平移、转向、倾斜 | 不能只按四人方向做简单平均，需支持位置差异 |
| 抓取/支撑实现思路 | 头顶被动支撑与主动抓取如何区分，人物与鱼缸怎样互相限制 | 不会靠“人物走远但仍无限抓住”掩盖问题 |
| 碰撞/失败思路 | 玩家碰撞、安全支撑柱、危险环境如何分层，如何避免错误碎裂 | 接触即碎规则不变，能记录触发原因 |

| 风险清单 | 最可能导致重构/失控的前三项技术风险、最小实验、备选方案 | 风险失败时知道何时停止扩展范围 |
| 第一份原型计划 | 第一份可试玩平地实验场具体测试哪些动作、需要多少临时工具 | 明确“能测/不能测”，不承诺未验证功能 |
| D-12 游戏内反馈 | 抓取成功、仅头顶支撑、抓取失败原因必须有可见且可辨认的原型反馈 | 不依赖调试日志就能看懂；反馈与真实抓取/支撑状态一致 |
| D-11 几何基线 | **先做一套**可调整的白盒鱼缸/人物几何比例；提供角色碰撞体、鱼缸尺寸、托举高度、四根安全支撑、有效抓取区的配置与记录方式 | 不需要 2–3 套候选，尺寸未冻结；可修改参数并复测换位/转向/跳跃/救援 |

### M0 另需专门评估的高风险事项
- **停车式检查点**：在首版不制作独立“主动放下/举起”功能的边界下，如何靠既有抓取、支撑、松手、重力和四根安全支撑自然停放并重新离开；如果不成立，要提出新需求并由主策划批准。
- **掉线与复位人数**：D-08 的三人继续与 V1.0 §6.4 的“四名玩家全部重生”如何兼容；当前不得凭空生成已断线的第四名玩家。
- **权威端断线**：D-09 四人异地联机下，如果承担权威计算的主机掉线，怎样满足 D-08 “其余三人继续”；须论证部署/迁移/容错策略，不能只演示普通客户端掉线。
- **事件竞争**：危险碰撞与停车激活接近同时发生、断线与复位重叠时，以何种顺序统一处理。
- **M3 完成判定**：原 V1.0 仅描述三段连续白盒，未明确终点触发与成功流程；在 M3 制作前需要补齐。

## 3. 可以临时决定什么，不能临时决定什么

- 程序可以自主选择刚体、约束、受控物理、网络框架、代码结构、开发分工和参数试验策略。
- 对原文件已经明确的行为（抓取点固定、无抓取不得主动水平搬运、鱼缸不自动扶正、接触危险即碎、单人坠落不重置鱼缸等），不得为了简单偷偷改掉。
- 以 V1.12 补充件及最新最终规则清单为准：D-01～D-12 均已确认。带有“建议实验默认”的内容只可用于临时试验，**须在版本说明中列明**，不能默认为正式玩法。
- 测试中发现某项需求显著超出成本或技术能力，反馈复现录像/截图、原因与替代办法，不要求硬撑一套不可控系统。

## 4. 建议首轮最小可测范围

**一片安全平地 + 四个临时角色 + 一个刚性鱼缸白盒体 + 自由底面抓取点的可视化工具（不固定四角站位）。**

先用 **D-11 C 的一套可调白盒比例**开展测试，不锁定抓取者四角站位。优先测试：四人同向前进/停止；三人前进一人后退；左右反向输入转向；松手后惯性与换位；某人受墙阻挡时角色与鱼缸的互相限制；共享状态早期联网试验。

成功标准不是“画面像成品”，而是：操作结果可预测、无持续弹飞或无限拉长、四人的作用均能被观察到、程序能定位异常来源。之后再加入跳跃、蹲下、危险碎裂、检查点和三关。

## 6. 完成 M0 之后再决定 M1 的范围

M0 不是“代码开工仪式”，而是做出可以被检验的方案。若某个技术风险会破坏共享抓取或可控性，应先缩小实验验证并拿给主策划试玩，不先堆大量关卡与正式资源。只有四真人能稳定玩，才算多人核心系统真正完成验证。
